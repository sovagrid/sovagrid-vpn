# SovaGrid VPN adapter

Здесь три раздельные возможности:

1. **Read-only инвентаризация Amnezia** для Hub. Root-процесс читает
   фиксированные конфиги и runtime-статус в известных контейнерах, чтобы
   проверить число гостей и работу интерфейсов. Ключи, UUID, адреса и исходные
   конфиги остаются только в памяти процесса и не публикуются. Контейнеры
   не меняются.
2. **Отдельный стандартный WireGuard** через `sovagrid_vpn.manage`. Он создаёт
   только собственные интерфейсы `sg…` и начинает работать лишь после явной
   команды `activate`. Существующие `wg0`, Amnezia и чужие файлы не принимаются
   под управление.
3. **Экспериментальное управление peer Amnezia AWG2/WireGuard** через
   `sovagrid_vpn.amnezia_admin`. Это отдельная root-only команда с явным
   закреплением точного контейнера. `enroll-preview` выдаёт безопасные ID и
   хеши для подтверждения в будущем графическом мастере; `enroll` повторно
   сверяет их перед записью состояния. Она может добавить или отозвать только
   собственный peer, проверяет весь конфиг и runtime, ведёт журнал отката.
   Для AWG3 и стандартного WireGuard она может создать клиентский `.conf` и
   выдать его только в зашифрованном конверте. Команда `settings-preview`
   проверяет закреплённый контейнер и показывает безопасную сводку настроек
   без записи или клиентских ключей. `settings-plan` добавляет только
   сверяемый по SHA и поколению предпросмотр числовых параметров AWG3;
   запись остаётся выключенной до миграции клиентских профилей и проверки
   параметров работающего интерфейса. Root-only CLI не устанавливается
   `run.sh`. Отдельный установщик брокера оставляет socket выключенным;
   каждый из двух контейнеров требует собственного root-only включения после
   закрепления Docker ID и проверки состояния. Agent передаёт только узкие
   операции брокера, включая предпросмотр плана; интерфейс панели для
   WireGuard догонит этот API.
   Подробности и границы применения — в
   [AMNEZIA_ADMIN.md](AMNEZIA_ADMIN.md).

## Что видит адаптер

Команда `docker container ls --all --format '{{json .}}'` выполняется на хосте.
На выход попадают только точные имена восьми известных контейнеров Amnezia,
их рабочее состояние, Docker health (если объявлен) и номера опубликованных
портов с TCP/UDP. Для `amnezia-awg2`, `amnezia-wireguard` и `amnezia-xray`
добавлен отдельный раздел `amnezia_details`: состояние runtime/реестра,
количество настроенных и работающих гостей, совокупный трафик и последняя
активность AWG/WireGuard. Образы, IP клиентов, адреса peer, логи, окружение,
тома, ключи, UUID, параметры Xray и конфиги никогда не попадают в JSON. Если
имя совпало, но образ не совпал с ожидаемым, состояние будет
`identity_mismatch`.

Запуск из каталога репозитория:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m sovagrid_vpn
```

На сервере для чтения Docker обычно требуются права root. Не добавляйте
непривилегированного SovaGrid Agent в группу `docker`: доступ к Docker socket
фактически даёт полномочия администратора хоста.

## Контракт для Hub

`sovagrid-blueprint/run.sh` устанавливает root-owned `systemd` timer: раз в 30
секунд он запускает этот CLI с `--output /var/lib/sovagrid/vpn/status.json
--group sovagrid-hub`. Файл создаётся атомарно с режимом `0640` в каталоге
root:sovagrid-hub `0750`. Hub читает этот каталог только через read-only mount,
проверяет схему и помечает снимки старше 90 секунд как `stale`. Agent не имеет
доступа к Docker и не нужен для инвентаризации VPN. Ошибка сбора показывается
как `source_status=error`, а не как отсутствие VPN. Вложенный раздел
`amnezia_details` имеет свою версию схемы: `schema_version=1`, `collected_at`,
`source_status` и `services`. Для каждой службы допустимы состояния `ready`,
`container_down`, `identity_mismatch`, `interface_down`, `process_down`, `registry_drift`,
`runtime_drift` и `error`. Числа недоступного источника передаются как `null`.

Тот же таймер независимо считывает **только собственные** WireGuard-инстансы
SovaGrid. В `managed.instances` передаются имя, вычисленное имя интерфейса,
UDP-порт, VPN-подсеть, число клиентов и состояние `active`, `stopped` либо
`error`. Для `active` проверяются работающий интерфейс, его адрес, порт и
точный набор peer. Ключи, адреса клиентов, endpoint и файлы профилей не
публикуются. Прерванная операция или расхождение конфигурации даёт
`state=error` только своему инстансу; поля, которые нельзя подтвердить,
передаются как `null`. Операция чтения не восстанавливает транзакцию и не
меняет конфигурацию. Если общее управление удерживает блокировку дольше пяти
секунд, текущий снимок WireGuard помечается `source_status=error`; следующий
запуск таймера повторит чтение. Если Docker недоступен, `source_status` Amnezia будет
`error`, но `managed` продолжит обновляться. Таймеру нужны права чтения
статуса интерфейса через netlink (`CAP_NET_ADMIN`), при этом он выполняет
только фиксированные команды просмотра.

Пример схемы:

```json
{"schema_version":1,"collected_at":1,"source":"docker_cli","source_status":"ok","services":[{"name":"amnezia-awg2","service":"AmneziaWG (awg2)","state":"running","health":"not_reported","published_ports":[{"port":51820,"protocol":"udp"}]}],"amnezia_details":{"schema_version":1,"collected_at":1,"source_status":"ok","services":[{"name":"amnezia-awg2","status":"ready","configured_clients":2,"runtime_clients":2,"awg3_fields":true,"active_last_3m":1,"latest_handshake_at":1,"received_bytes":1024,"sent_bytes":2048}]},"managed":{"source_status":"ok","instances":[{"name":"phone-vpn","interface":"sg615ed6c9020","port":51821,"subnet":"10.49.0.0/24","client_count":1,"state":"active"}]}}
```

Для предварительной оценки отдельного **нового** WireGuard-инстанса остаётся
неисполняемый dry-run:

```sh
python3 -m sovagrid_vpn --plan-wireguard demo-vpn --port 51820 --subnet 10.49.0.0/24
```

Он проверяет формат параметров и столкновение с Docker-портами Amnezia.
Поле `can_apply` всегда `false`. Этот старый план ничего не устанавливает.
Реальное развёртывание выполняется только через отдельный root-only CLI ниже.

## Управляемый WireGuard: установка и применение

На Ubuntu-хосте, где установлен только Agent, брокер можно подготовить отдельно
из проверенного пакета VPN, перенесённого SovaGrid. Root-only установщик
`deploy/install-wireguard-control.py` сначала отдаёт read-only `preview` с
`state_revision`, затем принимает `apply --expected-state REVISION`. Перед
записью он повторно сверяет эту ревизию, оба root-owned дерева исходников,
принадлежность существующих файлов и общий lock пакета. Пакеты
`wireguard-tools`, `iproute2`, `python3-cryptography` (и `apparmor`, если нужен
парсер действующего профиля) устанавливаются при отсутствии; для действующего
профиля `wg-quick` узкий AppArmor-helper добавляет правило чтения собственной
конфигурации. Затем установщик включает ограниченный Unix-сокет, брокер и
отдельный таймер санитизированного VPN-инвентаря. На Agent-only хосте таймер
использует шаблон `sovagrid-vpn-status-agent.service` и сохраняет снимок в
`/var/lib/sovagrid-vpn-inventory/status.json` с правами `root:sovagrid 0640`
в каталоге `root:sovagrid 0750`. Agent может читать этот снимок, не получая
доступа к закрытым VPN-ключам. Текущая версия Agent ещё не передаёт этот
снимок в Hub: удалённая панель VPN требует отдельного маршрута Agent→Hub.
VPN-интерфейс и клиенты не создаются.

```sh
cd /opt/sovagrid-src/sovagrid-vpn
sudo python3 -I -B deploy/install-wireguard-control.py preview
sudo python3 -I -B deploy/install-wireguard-control.py apply --expected-state REVISION_FROM_PREVIEW
```

При прерывании сохраняется закрытый журнал. `preview` покажет
`RECOVERY_REQUIRED`; `sudo python3 -I -B deploy/install-wireguard-control.py
recover` возвращает только собственные файлы, снимок и прежнее состояние
брокера и таймера, отказываясь перезаписывать чужие изменения. Для обновления
их файлов предварительно остановите и отключите broker socket/service и
status timer; работающий
WireGuard-интерфейс это не останавливает. Установленные через apt пакеты и
успешно добавленное локальное правило AppArmor остаются после отката файлов
брокера; их удаление может затронуть чужие VPN и выполняется отдельно.

`sudo ./run.sh --with-wireguard` из `sovagrid-blueprint` также ставит
локальный Unix-сокет `/run/sovagrid-vpn/control.sock` и отдельный root-процесс.
Основной процесс Agent с системным UID `sovagrid` отправляет проверенный запрос
напрямую в сокет; локальный root может использовать
`/usr/local/bin/sovagrid-vpn-ctl` с действиями `create`, `activate`,
`add-client`, `revoke-client`, `remove`, `instances`, `clients` и
`sealed-export` для выдачи зашифрованного клиентского профиля. Процесс повторно
проверяет точный порядок и формат аргументов, принадлежность инстанса SovaGrid
и состояние WireGuard. Он не принимает путь к файлу, произвольную команду,
произвольный `export-client` с путём или `recover`; из обычных результатов удаляется
путь закрытого профиля.
Сокет доступен только `root` и группе `sovagrid`, а процесс дополнительно
сверяет UID и PID с `MainPID` службы `sovagrid-agent.service` в systemd.
Это закрывает прямой вызов брокера из обычной команды под тем же UID.
Служба Agent по-прежнему работает без
root, с `NoNewPrivileges` и без Linux capabilities. Статус в панели
обновляется существующим таймером не позднее чем примерно через 30 секунд.
Если операция прервана, восстановление остаётся отдельной root-only командой
`python3 -m sovagrid_vpn.manage recover NAME` после проверки состояния.

Требуются Ubuntu с systemd, Python 3.10+, `python3-cryptography`,
`wireguard-tools` (`wg`, `wg-quick`), `iproute2` (`ip`) и поддержка WireGuard
ядром. Docker необязателен, но если
он установлен, CLI проверяет опубликованные порты и подсети его сетей и
останавливается при недоступном Docker daemon. Пакеты устанавливаются явной
административной командой; SovaGrid сам `apt` не запускает:

```sh
sudo apt-get update
sudo apt-get install -y wireguard-tools iproute2 python3-cryptography
sudo install -d -o root -g root -m 0700 /etc/wireguard
```

На Ubuntu с профилем AppArmor `/etc/apparmor.d/wg-quick` **до `activate`**
установите узкое локальное правило:

```sh
sudo env PYTHONDONTWRITEBYTECODE=1 python3 deploy/install-wg-quick-apparmor.py
```

Скрипт проверяет наличие `wg`, `wg-quick`, `ip`, `apparmor_parser` и профиля,
при необходимости создаёт `/etc/apparmor.d/local`, сохраняет все имеющиеся
локальные правила и добавляет только чтение
`/var/lib/sovagrid-vpn/*/server.conf` для `wg-quick`. Затем он проверяет
синтаксис полного профиля и перезагружает его. Повторный запуск не дублирует
правило. Код завершения `0` означает успех, `2` — ошибку; при ошибке
`activate` не запускайте, сначала исправьте указанную причину. На системе без
профиля `wg-quick` этот шаг не нужен. Временный файл для `wg syncconf`
создаётся с режимом `0600` внутри `/etc/wireguard`, поэтому дополнительное
правило для профиля `wg` не требуется.

Запускайте команды **из каталога этого репозитория**. Если проект поставлен
через `sovagrid-blueprint/run.sh`, это `/opt/sovagrid-src/sovagrid-vpn`. Команды ниже
используют другой порт и подсеть, чем действующие VPN; выберите свободные
значения и замените адрес в примере своим публичным IP или DNS:

```sh
sudo env PYTHONDONTWRITEBYTECODE=1 python3 -m sovagrid_vpn.manage create phone-vpn \
  --port 51821 --subnet 10.49.0.0/24 --endpoint vpn.example.com
sudo env PYTHONDONTWRITEBYTECODE=1 python3 -m sovagrid_vpn.manage activate phone-vpn
sudo env PYTHONDONTWRITEBYTECODE=1 python3 -m sovagrid_vpn.manage add-client phone-vpn iphone
sudo env PYTHONDONTWRITEBYTECODE=1 python3 -m sovagrid_vpn.manage clients phone-vpn
```

`create` только генерирует серверный ключ и закрытые файлы в
`/var/lib/sovagrid-vpn/phone-vpn/`; интерфейс, пакетные правила и работающие
VPN он не меняет. `activate` повторяет проверки и создаёт **только** ссылку
`/etc/wireguard/sg<хэш>.conf` на принадлежащую SovaGrid конфигурацию, затем
включает и запускает `wg-quick@sg<хэш>.service`. Имя интерфейса не принимает
пользовательский ввод и никогда не совпадает с обычным `wg0`. Предварительные
проверки отказывают при занятом UDP-порту, коллизиях с опубликованными
Docker-портами, пересечении подсетей хоста/Docker и существующем интерфейсе,
конфигурации или включённом чужом сервисе. Итоговый JSON не содержит ключей.

Профиль клиента сохраняется как `.../clients/iphone.conf` с режимом `0600`.
Его можно скопировать в другой **заранее созданный закрытый каталог**:

```sh
sudo install -d -o root -g root -m 0700 /root/vpn-exports
sudo env PYTHONDONTWRITEBYTECODE=1 python3 -m sovagrid_vpn.manage export-client \
  phone-vpn iphone --output /root/vpn-exports/iphone.conf
```

Импортируйте этот `.conf` в клиент WireGuard на телефоне по защищённому
каналу. Не публикуйте профиль в GitHub, Telegram или Hub: в нём приватный
ключ и общий ключ peer. Экспорт отказывается перезаписать существующий файл,
включая символьную ссылку; каталог назначения должен быть root-owned `0700`.

Для выдачи через веб-клиент брокер принимает `sealed-export NAME CLIENT
PUBLIC_KEY`, где `PUBLIC_KEY` — сгенерированная клиентом открытая точка P-256
в каноническом base64url без `=`. Под блокировкой он проверяет принадлежность
инстанса и точное соответствие профиля состоянию, затем шифрует его с новым
временным ключом P-256 через ECDH, HKDF-SHA256 и AES-256-GCM. Выход содержит
только `{version:1,ephemeral_public_key,salt,nonce,ciphertext}`; бинарные поля
закодированы base64url без `=`. Для HKDF используется ASCII строка
`SovaGrid sealed WireGuard profile v1`, а AAD — байты
`SovaGrid profile\0NAME\0CLIENT`. Секретный ключ получателя остаётся у клиента;
Agent и Hub могут передавать лишь зашифрованный контейнер. Максимальная длина
декодированного `ciphertext` — 4096 байт.

### Полный маршрут через собственный WireGuard

Обычные профили остаются split tunnel. Для полного IPv4-маршрута отдельная
root-only настройка `sovagrid_vpn.routing` создаёт **только** таблицу nftables
`ip sg...` для выбранного управляемого инстанса (имя вида
`sgvpn_sg615ed6c9020`). Таблица содержит одно правило masquerade для его
подсети; чужие таблицы и правила не меняются. Настройка также создаёт
root-owned политику и `sovagrid-vpn-routing.service`, который восстанавливает
правила после перезагрузки, и свой файл sysctl для
`net.ipv4.ip_forward=1`. Нужен установленный `nftables`. Каждое включение и
отключение требует свежий `state_revision` из `preview`; при чужом файле,
изменённом правиле или устаревшей ревизии операция отказывается продолжать.
На установленном сервере команды запускаются из `/opt/sovagrid-vpn`:

```sh
sudo apt-get install -y nftables
cd /opt/sovagrid-vpn
sudo python3 -B -E -S -m sovagrid_vpn.routing preview phone-vpn
sudo python3 -B -E -S -m sovagrid_vpn.routing arm phone-vpn --expected-state REVISION_FROM_PREVIEW
```

После `arm` сверьте `routing_configured:true`. Только при живом собственном
интерфейсе, включённой IPv4-пересылке, точном правиле NAT и работающей
политике восстановления брокер может выдать `sealed-export NAME CLIENT
PUBLIC_KEY --route full`. Профиль содержит
`AllowedIPs = 0.0.0.0/0, ::/0`: клиенту предлагается направить IPv6 в
туннель, но эта версия шлюза пересылает только IPv4. Проверьте на телефоне,
что IPv6 не обходит туннель; работоспособность IPv6-сайтов пока не обещается.
Поле `routing_configured` **не является проверкой доступа в Интернет**:
UFW, другие firewall-цепочки, облачная защита, закрытый UDP-порт или маршруты
провайдера могут блокировать пакеты. После импорта проверьте внешний IP и
доступность сайтов на реальном клиенте. Перезапуск или перезагрузка UFW/
другого firewall после `arm` может стереть правила; повторите `preview` и
`arm` с новой ревизией. Отключение удаляет только точную собственную таблицу,
файл sysctl и unit, когда больше нет включённых инстансов; текущее глобальное
значение `ip_forward` не сбрасывается, чтобы не оборвать чужие маршруты.

```sh
sudo python3 -B -E -S -m sovagrid_vpn.routing disarm phone-vpn --expected-state REVISION_FROM_PREVIEW
```

Добавление и отзыв клиента меняют только файлы этого инстанса. Перед первым
изменением CLI надёжно сохраняет закрытый журнал `transaction.json` (`0600`).
Если интерфейс активен, `wg syncconf` применяет изменение без полного
перезапуска. Команда сообщает об успехе только после проверки точного набора
peer, их ключей, адресов и порта работающего интерфейса. При ошибке журнал
сохраняется; прежнее состояние может оставаться активным. Повторите ту же
команду или выполните:

```sh
sudo env PYTHONDONTWRITEBYTECODE=1 python3 -m sovagrid_vpn.manage recover phone-vpn
```

Восстановление завершает зафиксированное намерение без создания второго ключа
или профиля. При постороннем изменении файлов либо работающего интерфейса оно
отказывает, сохраняя журнал для ручной проверки. Отзыв удаляет peer из
работающего интерфейса и его сохранённый профиль. Если копия профиля уже
выдана, она перестаёт авторизоваться именно **после успешного отзыва**; сама
копия с телефона не удаляется. Повтор выдачи уже существующего клиента и
повтор отзыва отсутствующего клиента безопасны и явно отмечены в JSON.

Для удаления собственного инстанса:

```sh
sudo env PYTHONDONTWRITEBYTECODE=1 python3 -m sovagrid_vpn.manage revoke-client phone-vpn iphone
sudo env PYTHONDONTWRITEBYTECODE=1 python3 -m sovagrid_vpn.manage remove phone-vpn --confirm-name phone-vpn
```

`remove` заранее проверяет все принадлежащие инстансу файлы и идентичность
активного интерфейса, затем останавливает/отключает только его systemd-unit,
удаляет созданную ссылку и свои ключи/профили. Чужие конфигурации или
неожиданные файлы приводят к отказу. Удаление ключей необратимо: сохраните
резервную копию закрытым способом, если она нужна.

Обычный профиль — **серверный split tunnel**: `AllowedIPs` содержит только
VPN-подсеть. Полный маршрут доступен лишь после отдельно включённого шлюза;
выдача такого профиля не открывает UDP-порт у провайдера/UFW и не заменяет
проверку реального клиента. Прежде чем импортировать профиль, администратор
должен разрешить выбранный UDP-порт в действующем сетевом экране и проверить
доступность сервера по его VPN-адресу.
Этот WireGuard не является AmneziaWG и не совместим с его клиентскими
профилями.

## Ограничения и дальнейшие шаги

- Состояние Docker-контейнера не доказывает, что VPN-клиент успешно соединится.
- Точная версия протокола AmneziaWG из имени контейнера не определяется.
- Read-only снимок Amnezia содержит агрегированные числа и статистику; он
  никогда не отдаёт исходный `wg/awg show dump`, поскольку первая строка
  содержит закрытый ключ интерфейса.
- Экспериментальный AWG2/WireGuard admin требует явного закрепления контейнера
  и отдельного окна обслуживания для каждой цели. Для AWG3 и WireGuard он
  формирует профиль по проверенным параметрам сервера и шифрует для ключа
  получателя. Синтетический AWG3 профиль
  успешно импортирован в официальный AmneziaVPN 5.0.1.5 на Android-эмуляторе:
  приложение распознало «AmneziaWG (version 3.1)». Проверка подключения
  реального телефона к действующему серверу и дальнейшего управления гостем
  через AmneziaVPN ещё нужна. Кнопки создания, экспорта и отзыва профиля в панели
  доступны только после отдельного opt-in брокера и закрепления точного
  контейнера администратором по [AMNEZIA_ADMIN.md](AMNEZIA_ADMIN.md). Сторонние
  peer не переходят под управление SovaGrid автоматически.
- Обновление образа, одновременная запись из AmneziaVPN, смена порта или
  параметров обфускации требуют отдельной процедуры: AmneziaVPN и SovaGrid
  не разделяют общий lock, а ранее выданные профили могут перестать работать.
- Xray VLESS изменяет файл `server.json` и требует рестарта текущего контейнера;
  для него нет проверенной операции без разрыва соединений, поэтому запись
  отключена.

## Граница управления через Hub

Локальный брокер предоставляет только фиксированный набор операций над
собственными стандартными WireGuard-инстансами. Hub должен проверять роль
пользователя и вести аудит до отправки действия Agent; брокер дополнительно
проверяет аргументы, UID и PID основного процесса Agent. Никакой операции управления Docker или
существующими Amnezia-контейнерами у него нет. Защищённый `sealed-export`
требует авторизации и аудита на стороне Hub, а также расшифровки только в
клиентском приложении. Резервные копии и ротация ключей требуют отдельных
операций с собственными проверками.
